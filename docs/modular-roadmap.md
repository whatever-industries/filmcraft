## Bin history performance

Compare Versions collects the revision list and both comparison endpoints during one verified walk from the project root. An editor can keep comparing the selected saves if a writer publishes another revision. The lookup keeps the two endpoint manifests in memory and requires no persistent index.

The first local macOS trial used 66 revisions and 96 filed sources. Reusing verified bin records across unrelated saves reduced the median warm query from 213 ms to 21 ms. A second trial measured the additional effect of the single history walk against that optimized baseline. The project had 257 revisions and 1,153 source clips. One bin held a cut trimmed after 255 unrelated saves. A second bin had been renamed on consecutive recent saves.

| Default comparison | First query with cold project files, before → after | Repeat query, before → after |
| --- | ---: | ---: |
| Cut with a distant previous version | 772 → 590 ms | 274 → 98 ms |
| Recently renamed bin | 592 → 595 ms | 96 → 94 ms |

Medians cover six cold queries and eighteen repeat queries per build and bin. Each session opened the project and browsed the selected bin before timing the desktop engine command. Immediately before each cold query, the trial evicted the project's manifest and record pages and verified zero resident pages. Both builds returned identical revision lists, endpoints and reports in each scenario. These measurements cover local APFS. A cold comparison took roughly 0.6 seconds. The desktop now runs the same read-only query on a single background worker. A rendered test holds that worker busy, leaves the comparison, opens another bin and verifies that only the new bin’s result appears. The CLI continues to return the report directly.

### Find Uses performance

The current reader verifies the saved records on each search. A local prototype retained the reverse item references, sequence names and explicit bin filings from that same verification pass. On an Apple M2 Max with local APFS, building this in-memory index cost about one ordinary search. On repeat searches within the same revision, the median lookup for a source used in 287 cuts was 0.11 ms.

| Backend operation | Latest save, warm file pages | Previous save, warm file pages | Oldest of 257 saves, warm file pages |
| --- | ---: | ---: | ---: |
| First ordinary search in a fresh process | 205 ms | 198 ms | 124 ms |
| Repeat ordinary search | 196 ms | 198 ms | 119 ms |
| Build the verified in-memory index | 195 ms | 197 ms | 119 ms |
| Query the retained index, median across items | 0.004 ms | 0.004 ms | 0.001 ms |
| Read, checksum and query a serialized index alone | 2.1 ms | 2.1 ms | 0.3 ms |
| Reload plus recheck history and all source record digests¹ | 107 ms | 109 ms | 111 ms |

The two-save project had 4,096 source clips, 288 sequences, 66 bins and 8,704 timeline entries. The newer save renamed the cuts bin and replaced one clip reference. Queries covered heavily reused footage, a nested cut and an item with no uses. The deep-history project had 1,153 source clips and one sequence. Each case used three fresh processes. Each process queried every selected ID three times. All 117 comparisons matched the ordinary reader’s complete report, including IDs, paths, direct and indirect uses, and secondary filings. Timings measure backend calls in the optimized development test profile. Desktop rendering and shared storage were outside the trial.

For a cold first search of the heavily used clip, the ordinary reader took **1,165 ms**, building and querying the memory index took **1,152 ms**, and reopening the saved index with full digest checks took **1,067 ms**. These are medians of three rotating runs per method with zero resident project and index file pages verified before each run. Device caches could still be warm. The latest revision’s serialized prototype occupied 158 KB and took 12 ms to write and sync once built.

¹ The warm figure sums the paired reload and full recheck timings. The cold trial timed them together. Checking integrity matters even when a revision ID matches. Changing an unrelated item in a disposable copy while preserving its size and modification time left the revision and index intact. A fresh scan still returned all 287 verified matches and correctly flagged the damaged item.

**Next milestone.** Build the index lazily when Find Uses first opens, retain at most one revision per Bin History browser, and describe results as verified at search time. Refresh must reread the records and surface new damage. Opening another document or choosing another revision must discard the old index. Copy, paste and recovery must continue verifying their required records independently. Measure actual desktop latency and retained memory with the same workload before considering an on-disk cache.

## Prototype audit

The prototype on `codex/modular-project-storage` was inspected at `2e02805d` with its local changes, including the uncommitted exchange and comparison implementations. The following is a source audit of those changes. Its tests describe behavior to reproduce on integration.

- **Bin exchange.** The bin-exchange panel calls `file.importProjectBin` to preview a dependency subset, including offline sources. Apply supplies the preview manifest. The exchange handler reads `Folder::load_subset`, checks that revision, rebases paths and calls `copy_selected_bin` inside one Undo step. The prototype test `import_previews_then_remaps_references_and_undo_removes_only_the_import` covers that path. Integration already rescues a historical subtree with dependencies to a standard file. Port preview, stale-preview rejection and single-step import over that traversal. Before implementation, decide when importing twice should reuse an existing source versus create an independent identity.
- **Side-by-side version comparison.** The versions panel calls `project.compareModuleVersions`; the discovery handler calls `Folder::version_subset` and compares the result with another revision or the open project. It reports member or clip changes and changed sources. The prototype UI test `deleted_cut_can_be_found_compared_and_recovered_from_the_file_menu` and `search_deleted_by_old_path_then_compare_and_recover_without_changing_live_items` cover that workflow. Integration now [compares two saved revisions](project-files.md#compare-two-saved-revisions) by bin or sequence ID. Bin History now uses these reports to copy either saved version into a writable bin. Review replacement of live edits, changed dependencies, and cross-bin moves separately from comparison and restore-as-copy.
